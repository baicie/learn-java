# 基于身份的产品体验设计

## 1. 目的

本文定义 AegisOps Portal 在不同身份登录后的最终产品形态，回答以下问题：

1. 用户登录后首先看到什么。
2. 左侧菜单有哪些模块。
3. 每个页面能看什么、能做什么。
4. 不具备权限的能力如何表现。
5. 当前实现与目标产品之间还差什么。

本文以四个内置角色为默认身份模型。自定义角色仍按权限组合动态生成界面，不额外维护一套页面。

## 2. 产品体验原则

### 2.1 同一个产品，不做四套后台

所有身份共用同一套 Portal 壳层：

```text
┌──────────────────────────────────────────────────────────┐
│ AegisOps / 当前租户                   搜索  通知  个人菜单 │
├──────────────┬───────────────────────────────────────────┤
│ 权限化侧栏   │ 页面标题、关键指标、待办、业务内容         │
│              │                                           │
│ 工作台       │ 页面内按钮继续按权限收敛                   │
│ 事件处置     │ 无权限能力不展示；直接访问返回 403         │
│ 资源中心     │                                           │
│ 自动化       │                                           │
│ 工作记录     │                                           │
│ 平台管理     │                                           │
└──────────────┴───────────────────────────────────────────┘
```

角色只决定默认权限和首页重点，不决定独立前端应用。

### 2.2 首页围绕待处理事项

首页不是固定大屏，也不是所有人看到相同统计。它应优先回答：

```text
现在有什么需要我处理？
哪些 Incident 正在影响业务？
我可以采取什么下一步动作？
```

### 2.3 前端隐藏不是安全边界

- 无权限菜单不显示。
- 无权限按钮不显示，不用 disabled 暗示隐藏能力。
- 用户直接输入 URL 时，路由守卫返回 403。
- 后端 API 始终再次校验权限、租户和数据范围。

## 3. 身份定义

| 角色代码        | 产品显示身份 | 核心职责                        | 默认数据范围 |
| --------------- | ------------ | ------------------------------- | ------------ |
| `system_admin`  | 系统管理员   | 租户、接入、权限与全局安全治理  | 全租户       |
| `record_admin`  | 运维负责人   | Incident 处置、审批、复盘和运营 | 全租户       |
| `normal_user`   | 运维工程师   | 一线排障、交接和本人工作记录    | 本人/被指派  |
| `readonly_user` | 观察者       | 查看运行态、处置结果和本人记录  | 只读可见范围 |

`record_admin` 保留现有代码以兼容数据库和 API，但 UI 文案使用“运维负责人”，避免把角色理解成只管理工作记录。

## 4. 目标导航结构

| 导航分组 | 页面                 | 系统管理员 | 运维负责人 | 运维工程师 | 观察者   |
| -------- | -------------------- | ---------- | ---------- | ---------- | -------- |
| 工作台   | 个性化工作台         | 是         | 是         | 是         | 是       |
| 事件处置 | Incident 中心        | 是         | 是         | 是         | 只读     |
| 事件处置 | 告警事件             | 是         | 是         | 是         | 只读     |
| 资源中心 | 资源                 | 管理       | 只读       | 只读       | 只读     |
| 资源中心 | 数据源               | 管理       | 只读       | 否         | 否       |
| 自动化   | Runbook              | 管理       | 管理       | 只读       | 只读     |
| 自动化   | 自动化任务           | 全部       | 审批/查看  | 申请/查看  | 只读     |
| 工作记录 | 工作记录             | 全部       | 全部       | 本人       | 本人只读 |
| 工作记录 | 运营中心             | 是         | 是         | 交接/待办  | 否       |
| 平台管理 | 模板、字典、工作日历 | 管理       | 管理       | 只读       | 只读     |
| 平台管理 | 用户、角色、权限     | 是         | 否         | 否         | 否       |
| 平台管理 | 审计日志             | 是         | 按需授权   | 否         | 否       |

菜单是否出现仍以权限为准。上表描述内置角色的目标默认授权，不覆盖租户自定义角色。

## 5. 各身份登录后的产品形态

### 5.1 系统管理员

#### 首屏

系统管理员进入“系统工作台”，重点是平台可用性和风险：

- 活跃 Incident、严重告警和待审批自动化。
- 数据源健康度、最近同步失败和采集延迟。
- 资源总量及未识别、冲突资源。
- 高风险权限变更和最近审计事件。
- 快捷入口：添加数据源、导入资源、创建用户、配置角色。

#### 侧栏

显示全部分组：工作台、事件处置、资源中心、自动化、工作记录、平台管理。

#### 可执行动作

- 管理数据源、资源、用户、角色和权限。
- 查看并处置所有 Incident。
- 管理 Runbook，审批和执行自动化。
- 管理工作记录模板、字典和工作日历。
- 查看审计日志。

系统管理员拥有兜底能力，但日常 Incident 审批仍建议由运维负责人完成，避免平台管理与生产处置长期混在一个账号上。

### 5.2 运维负责人

#### 首屏

运维负责人进入“处置工作台”，重点是团队当前负载：

- 未确认、处理中和已超 SLA 的 Incident。
- 待审批自动化和待处理工作记录审批。
- 当班人员、待交接事项和团队工作量。
- 最近 AI 诊断结果、推荐 Runbook 和复盘待办。

#### 侧栏

```text
工作台
事件处置
  Incident 中心
  告警事件
资源中心
  资源
  数据源（只读）
自动化
  Runbook
  自动化任务
工作记录
  工作记录
  运营中心
平台管理
  模板管理
  字典管理
  工作日历
```

不显示用户管理、角色管理和系统级接入密钥。

#### 可执行动作

- 查看全部 Incident，更新状态、负责人、时间线和复盘。
- 触发 RCA/AI 诊断并审核诊断结果。
- 管理 Runbook，审批自动化任务。
- 查看全部工作记录，处理审批、交接和统计。
- 管理模板、字典和工作日历。

### 5.3 运维工程师

#### 首屏

运维工程师进入“我的工作台”，只显示与本人相关的事项：

- 分配给我的 Incident。
- 我的待办、待交接和待补充证据事项。
- 我最近处理的 Incident 和工作记录。
- 可使用的 Runbook 与已批准自动化任务状态。
- 快捷入口：新建工作记录、接收交接、查看我的 Incident。

#### 侧栏

```text
工作台
事件处置
  Incident 中心
  告警事件
资源中心
  资源
自动化
  Runbook
  自动化任务
工作记录
  工作记录
  运营中心（仅交接和本人待办）
平台管理
  模板（只读）
  字典（只读）
  工作日历（只读）
```

#### 可执行动作

- 查看本人负责或参与的 Incident，补充时间线和证据。
- 触发诊断、查看推荐 Runbook。
- 提交自动化申请并查看执行日志，但不能自行审批。
- 创建、编辑本人工作记录，参与评论、附件和关联。
- 处理分配给本人的审批任务和交接任务。

当前 `automation:execute` 同时表达“创建”和“执行”，粒度过粗。在拆出 `automation:request` 之前，不应把 `automation:execute` 默认授予普通用户。

### 5.4 观察者

#### 首屏

观察者进入“运行概览”，只展示只读信息：

- 当前 Incident 数量、影响等级和处理进度。
- 最近告警和资源健康概况。
- 最近完成的自动化结果。
- 本人可见的工作记录。

首页不出现“新建”“编辑”“审批”“执行”“导入”等操作入口。

#### 侧栏

```text
工作台
事件处置
  Incident 中心（只读）
  告警事件（只读）
资源中心
  资源（只读）
自动化
  Runbook（只读）
  自动化任务（只读）
工作记录
  工作记录（本人只读）
平台管理
  模板、字典、工作日历（只读）
```

观察者不能通过页面或 API 改变任何业务状态。审计日志不默认开放；审计人员应使用单独的自定义角色获得 `audit:read`。

## 6. 页面内权限表现

### 6.1 Incident 详情

所有可见身份看到同一条证据链：基本信息、影响范围、告警、时间线、指标/日志证据、AI 诊断、Runbook 建议、自动化记录和复盘。

| 动作              | 系统管理员 | 运维负责人 | 运维工程师 | 观察者 |
| ----------------- | ---------- | ---------- | ---------- | ------ |
| 查看证据链        | 是         | 是         | 可见范围内 | 是     |
| 更新状态/负责人   | 是         | 是         | 被指派时   | 否     |
| 触发诊断          | 是         | 是         | 被指派时   | 否     |
| 编辑 Runbook      | 是         | 是         | 否         | 否     |
| 提交自动化申请    | 是         | 是         | 是         | 否     |
| 审批自动化        | 是         | 是         | 否         | 否     |
| 查看执行日志/复盘 | 是         | 是         | 可见范围内 | 是     |

### 6.2 工作记录

- 系统管理员、运维负责人默认查看全部记录。
- 运维工程师查看本人创建或负责的记录，可新增和编辑。
- 观察者只查看本人记录，不显示编辑入口。
- 模板、字典、日历对普通用户和观察者保持只读，用于正确渲染记录内容。

### 6.3 平台管理

- 用户和角色管理只对系统管理员显示。
- 运维负责人管理业务配置，不管理账号与权限。
- 普通用户和观察者只能读取表单渲染所需的模板、字典和日历。
- 数据接入密钥、采集权限和租户配置不出现在非管理员界面。

## 7. 当前实现与目标态差距

### 7.1 当前已经具备

- 权限化侧栏、路由守卫和页面按钮守卫。
- 四个内置角色与工作记录数据范围。
- 工作记录、运营中心、资源、数据源和平台 IAM 页面。
- 系统管理员拥有完整 AIOps 权限目录。

### 7.2 当前实际登录效果

| 身份       | 当前主要可见内容                                                            |
| ---------- | --------------------------------------------------------------------------- |
| 系统管理员 | 当前 Portal 全部页面，包括数据源、资源、工作记录和平台管理                  |
| 运维负责人 | 工作记录、运营中心、模板、字典、日历；没有 Incident/告警/自动化 Portal 页面 |
| 运维工程师 | 本人工作记录、交接/审批入口、模板/字典/日历只读                             |
| 观察者     | 本人工作记录及模板/字典/日历只读                                            |

### 7.3 必须补齐的产品缺口

1. Portal 尚无 Incident、告警、Runbook、自动化任务和审计日志页面。
2. AIOps 权限目前只默认授予 `system_admin`，其他内置角色还没有目标默认授权迁移。
3. 当前工作台对所有角色使用同一套工作记录指标和快捷入口，未按权限裁剪。
4. 当前工作台的“新建工作记录”等快捷入口仍可能让只读用户进入 403，应改为权限化快捷入口。
5. `normal_user` 需要“提交自动化申请”的独立权限，不能复用高风险执行权限。

因此，当前 Portal 是“工作记录管理面 + 资源接入基础”，还不是本文描述的完整 FaultLens Incident 工作台。

## 8. 默认权限目标

以下是目标原则，不在本文中直接修改数据库授权：

- `system_admin`：保留全部权限。
- `record_admin`：增加资源/数据源只读、告警读取、Incident 读写与诊断、Runbook 管理、自动化读取与审批。
- `normal_user`：增加资源/告警/Incident/Runbook 读取，以及本人 Incident 处置和自动化申请能力。
- `readonly_user`：增加资源、告警、Incident、Runbook 和自动化结果的只读权限。
- `datasource:ingest`、`admin:manage`、平台用户/角色写权限不授予非系统管理员。
- `automation:approve`、`automation:execute` 不授予普通用户和观察者。

数据范围必须与动作权限同时生效，不能只靠角色名判断。

## 9. 验收标准

### 9.1 通用验收

- 每个内置角色登录后只看到有权限的菜单和快捷入口。
- 页面按钮、路由守卫和后端 API 使用同一权限码。
- 直接访问无权限 URL 返回 403，不泄露目标资源信息。
- 角色切换或权限更新后，重新加载授权快照即可得到一致界面。

### 9.2 角色验收

- 系统管理员可以完成接入、授权、处置、审批和审计闭环。
- 运维负责人可以完成 Incident 从确认到复盘的闭环，但不能管理用户和角色。
- 运维工程师可以完成本人 Incident、交接和工作记录任务，不能自批自动化。
- 观察者全程只读，界面不出现写操作入口。

## 10. 非目标

- 不为每个角色复制一套页面。
- 不把角色名硬编码进业务组件。
- 不在本阶段设计复杂组织层级、跨租户角色继承或 ABAC 规则引擎。
- 不为“最终形态”提前实现尚未进入当前 Phase 的页面。

## 11. 后续实施顺序

1. 先把现有工作台和快捷入口改为权限驱动。
2. 按 MVP 闭环补 Incident 中心及详情页。
3. 接入告警、Runbook 和自动化任务页面。
4. 新增非管理员内置角色的 AIOps 默认授权迁移。
5. 最后补审计日志页和角色化首页指标。
